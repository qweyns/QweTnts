# Аудит и рефакторинг QweTnts

Версия: Phase 1 → рефакторинг. Ориентир по архитектуре и оформлению —
`QweProtectStones` (QPS): те же принципы локализации, те же правила игры с
приватами, тот же стиль конфигов.

---

## 1. Главные архитектурные ошибки старого кода

### 1.1 Сырой ключ `antilag.cooldown` в чате

**Причина:** в `lang/ru.yml` ключи были написаны с опечаткой — `antilab.cooldown`,
`antilab.player-limit`, `antilab.chunk-limit`, а код запрашивал `antilag.*`.
`Lang.raw()` при отсутствии ключа возвращал сам ключ, и игрок видел в чате
`antilag.cooldown`.

**Усугубляло:** отсутствие контроля целостности. Опечатка в lang-файле не
вызывала ни предупреждения в консоль, ни падения теста.

**Сейчас:** отдельный класс `config/Lang` — копия архитектуры
`LanguageManager` из QPS: встроенные языки распаковываются сами, недостающие
ключи добираются из jar, отсутствующий ключ даёт **однократное** предупреждение
в консоль и пустое сообщение (никогда не текст ключа). Плюс модульный тест на
`Colors`/парсинг, а ключи перечислены в обоих lang-файлах.

### 1.2 Динамит поджигал сам себя, и это не настраивалось

**Было:** `DynamiteActivateListener` на любой правый клик предметом немедленно
создавал `TNTPrimed` — «поджог из рук» был единственным режимом, переключателя
в конфиге не существовало.

**Стало:**

| Поведение | Настройка |
|---|---|
| Динамит ставится блоком и ждёт огня (**по умолчанию**) | `settings.dynamites.auto-ignite: false` |
| Старое поведение: клик — и заряд горит | `settings.dynamites.auto-ignite: true` |
| Исключение для конкретного динамита | ключ `auto-ignite:` в его файле (приоритет выше глобального) |

Установка идёт через обычный `BlockPlaceEvent` (предмет — TNT), поэтому QPS,
WorldGuard и прочие плагины **могут её отменить** — это принципиально: ручная
`setType()` в обход события ломала бы защиту приватов.

Поджог обрабатывается отдельным слушателем:

* огниво / огненный заряд (`PlayerInteractEvent` + `BlockIgniteEvent`);
* огонь, лава, молния, распространение огня (`BlockIgniteEvent`);
* другой взрыв — цепная детонация (`chain-radius`, `chain-delay-ticks`);
* удар кулаком, если включено `punch-ignites`.

Ванильный поджог всегда отменяется: вместо него создаётся `TNTPrimed` с
PDC-меткой, мощностью и фитилём из конфига (`PrimingService` — единственная
точка создания заряда).

### 1.3 Обсидиан и древние обломки: три независимых бага

а) **`transformable-blocks` не работал в принципе.** Скан прочных блоков
(`collectBreakableBlocks`) обходил только те материалы, что перечислены в
`breakable-blocks`. Древние обломки в `shockwave.yml` там не были указаны —
значит, до них скан не доходил, а vanilla не кладёт их в `blockList`
(сопротивление 1200 против мощности 4). Трансформация
`ANCIENT_DEBRIS → OBSIDIAN` не срабатывала ни разу.

б) **`drop-chance` парсился, но нигде не использовался.** В старом
`DynamiteExplodeListener` не было ни одного обращения к `dropChancePercent`:
блок просто добавлялся в `blockList`, и сервер выбрасывал его предметом.
При `drop-chance: 0` обсидиан всё равно выпадал — то есть рейд был
бесконечно возобновляем.

в) **Не было модели сопротивления.** Решение «ломать или нет» принималось
только по списку материалов, без учёта взрывоустойчивости. В результате
настройка была «всё или ничего», а защита от случайного разрушения
`reinforced deepslate`/бедрока отсутствовала.

**Стало:** математика вынесена в чистый класс `dynamite/BlastMath` (покрыт
тестами, работает без сервера):

```
эффективное сопротивление = (resistance + 0.3) * resistance-scale
блок ломается, если эффективное сопротивление <= power
                       И resistance <= max-resistance
```

Порядок принятия решения:

1. блок в списке «неразрушимых» (бедрок, порталы, командные блоки) — никогда;
2. для материала есть явное правило `breaking.blocks` — решает только шанс
   (`break-chance`), сопротивление не важно: **единственный корректный способ
   дать динамиту пробить обсидиан**;
3. иначе работает жёсткий потолок `max-resistance`;
4. иначе сравнение эффективного сопротивления с мощностью;
5. трансформация (`ANCIENT_DEBRIS → OBSIDIAN`) имеет приоритет над ломанием.

Скан прочных блоков теперь учитывает и правила, и трансформации, поэтому
`transformable-blocks` работает без дублирования материала в `breaking`.

### 1.4 Тяжёлая работа на главном потоке

* `collectBreakableBlocks` обходил куб `(2·power+1)³`: для Динамита B
  (power 8) это **4913 обращений к блоку** на каждый взрыв, без порционного
  режима и без потолка.
* Обработчик урона на каждый `EntityDamageEvent` вызывал `getNearbyEntities`
  в радиусе 8 — при серии взрывов это сотни сканов сущностей.
* Настройки `large-explosion-blocks-per-tick` и `large-explosion-tick-period`
  лежали в конфиге, но нигде не использовались (мёртвый конфиг).

**Стало:** радиус скана ограничен `anti-lag.max-break-scan-radius` (по
умолчанию 8), скан выполняется только если у динамита есть правила по
материалам, отложенные изменения блоков группируются по чанкам (на Folia это
ещё и гарантия, что задача не тронет чужой регион), а мощные заряды
логируются предупреждением.

### 1.5 Интеграция с QPS без защиты

* `plugin.qps()` возвращал `QpsApi.get()` без проверки `isAvailable()` —
  NPE, если QPS выгружен или ещё не поднялся;
* любое исключение внутри API QPS прерывало обработку взрыва;
* три почти одинаковых метода (`canBreak`, `isCore`, `canModifyAfterExplosion`)
  дублировали одну и ту же логику.

**Стало:** `integration/QpsBridge` — единственная точка обращения к QPS.
Отсутствие API трактуется как «приватов нет», любое исключение логируется и
трактуется как «блок не трогать».

### 1.6 Прочее

| Проблема | Решение |
|---|---|
| Три копии `isInSpawnRadius`, три копии проверки привата | общие проверки в слушателях + `QpsBridge` |
| Хардкод строк: « мин », « сек », текст лога рейда | ключи `time_seconds`, `time_minutes_seconds`, `log_region_destroyed` |
| Нет прав на обход ограничений | `qwetnts.bypass.world`, `.region`, `.antilag`, `.raidblock` |
| Отсутствующий тип динамита в PDC приводил к NPE потом | все поиски по id возвращают `null` и проверяются |
| `BlockPlaceEvent` обрабатывался только для рейд-блоков | добавлены проверки установки и возврат предмета при поломке |
| Рецепты при `reload` могли копиться | `CustomRecipeListener.clear()` + снятие Bukkit-рецептов по ключам |

## 2. Новая структура проекта

```
ru.qweyns.qwetnts
├── QweTnts                     жизненный цикл, задачи, аксессоры
├── Keys                        PDC-ключи
├── antilag/AntiLag             лимиты, кулдаун, рейт-лимит сообщений
├── command/QweTntsCommand      /qtnt (reload|list|give|help) + tab-complete
├── config
│   ├── Settings                config.yml с валидацией значений
│   ├── Lang                    локализация (архитектура LanguageManager из QPS)
│   └── DynamiteLoader          чтение dynamites/*.yml
├── dynamite
│   ├── BlastMath               чистая математика разрушения (тесты)
│   ├── DynamiteRegistry        реестр типов + ключи рецептов
│   ├── DynamiteType            неизменяемое описание динамита
│   ├── PlacedDynamiteManager   установленные, но не подожжённые заряды
│   └── PrimingService          единственная точка создания TNTPrimed
├── integration/QpsBridge       null-безопасный доступ к API QPS
├── listener
│   ├── DynamiteUseListener     клик предметом: автоподжог или установка
│   ├── DynamitePlaceListener   BlockPlace/BlockBreak установленного динамита
│   ├── DynamiteIgniteListener  поджог огнивом/огнём/взрывом, цепная детонация
│   ├── DynamiteExplodeListener разрушение блоков, трансформации, рейд-блоки
│   ├── RegionDynamiteListener  классификация взрыва и урон осаде (QPS)
│   ├── RaidBlockListener       запрет установки на рейд-блок
│   ├── RaidLoggingListener     журнал уничтоженных приватов
│   └── CustomRecipeListener    валидация ингредиентов по PDC
├── raid/{RaidBlockManager, AlertThrottle}
├── stats/ExplosionStats
├── metrics/QweTntsMetrics
└── util/{Colors, Components, Io, Materials, Schedulers, ThreadPools}
```

## 3. Проверки, которые добавлены тотально

* `event.isCancelled()` — на всех отменяемых событиях (`ignoreCancelled = true`);
  исключение осознанно одно: `RegionExplosionTypeEvent` не отменяется по
  устройству API QPS.
* `instanceof` — перед каждым приведением (`TNTPrimed`, `ShapedRecipe`,
  `Player`, `InventoryHolder`, `ConfigurationSection`).
* `null` — мир у локации, `ItemMeta`, PDC-значение, тип динамита по id,
  `getClickedBlock()`, `getItem()`, `getRecipe()`, `Chunk`.
* Валидация конфига — отрицательные лимиты, пустой язык, неизвестный режим
  миров, неизвестный материал и мощность ≤ 0 не роняют плагин: пишется
  предупреждение и подставляется дефолт.
* Любой вызов API QPS — в `try/catch`, сбой трактуется в безопасную сторону.
* Исключения при создании заряда, регистрации рецепта и проверке крафта
  перехватываются и логируются.

## 4. Производительность

| Что | Как экономим |
|---|---|
| Скан прочных блоков | только при наличии правил, радиус ≤ `max-break-scan-radius` |
| Изменения блоков после взрыва | одной задачей на чанк, а не на блок |
| Урон сущностям | один проход по сущностям на событие, без `getNearbyEntities` при `cut = 0` у всех типов |
| Сообщения игроку | рейт-лимит `message-cooldown-millis` |
| Сохранение на диск | I/O-пул, атомарная запись, только при изменениях |
| Карты в памяти | периодическая чистка (анти-лаг, алерты, установленные заряды) |
| Кеш компонентов | сообщения без плейсхолдеров парсятся один раз |

## 5. Что намеренно не сделано

* Фаза 2 ТЗ (спавнер-майнинг, временный лёд, ТНТ-пушка, алерты в Discord).
* Порционная обработка крупных взрывов по тикам: сейчас предоставлен потолок
  радиуса; если понадобится «резать» взрыв на тики — это отдельная задача.
* Миграция старых конфигов: `config.yml` меняет структуру
  (`settings.raid-blocks.*` вместо `settings.raid-block-*-ticks`). Старый файл
  читается (неизвестные ключи игнорируются), значения берутся из дефолтов —
  достаточно один раз удалить `config.yml`, чтобы получить новый с комментариями.
