# Чего ещё можно добавить: сверка с HolyWorld Lite

Документ — ответ на вопрос «что разработчики HolyWorld добавили бы сюда
ещё». Основа: вики HolyWorld Lite (`lite/region/tnt.md`,
`lite/region/region.md`, `lite/events/castle.md`), исходники
QweProtectStones 2.0.0 и полный аудит кода (`docs/AUDIT.md`, §10).

Здесь **только планы**: ничего из перечисленного не реализовано и не
согласовано. Напротив каждого пункта — обоснование и оценка стоимости.

---

## 3. Спецификации

### P1. Неразрушающий динамит: Стиллер, Надёжный стиллер, Ледяная волна

> **Готово.** Ключ `breaking.destructive` в record `Breaking`, три файла
> в `dynamites/`, попутно закрыт дефект 10.3.7 (спавнеры теперь ищутся
> досмотром, когда список vanilla не используется).

**Суть HW.** Стиллер не ломает ни одного блока, но выбивает спавнер
(шанс 50 %). Надёжный стиллер — то же с шансом 75 %, собирается из двух
стиллеров. Ледяная волна тоже не трогает рельеф, но заливает сферу
радиусом 2 льдом на 5 секунд.

**Что добавить.** Один ключ:

```yaml
breaking:
  # false — динамит НЕ разрушает блоки: рельеф остаётся целиком.
  # Спавнеры, эффекты, временные блоки и райд-метки при этом работают.
  destructive: true
```

Дальше в `onExplode`:

* если `!destructive` — `event.blockList().clear()` **до** обработки
  (сейчас это делается только при `vanilla-blocklist: false`);
* `processBlockList` при неразрушающем динамите не нужен, но
  `scanHardBlocks` должен искать **спавнеры** (это и есть фикс 10.3.7):
  `SPAWNER` добавляется в интересующие материалы, когда
  `spawner-mining.enabled`;
* временные блоки и райд-метки работают как обычно.

**Три файла в комплекте:**

| Файл | Ключевое |
|---|---|
| `stiller.yml` | `destructive: false`, `spawner-mining.chance: 50`, без `breaking.blocks` |
| `reliable_stiller.yml` | `destructive: false`, `spawner-mining.chance: 75`, рецепт из двух `tnt:stiller` |
| `ice_wave.yml` | `destructive: false`, `temporary-blocks`: `material: ICE`, `radius: 2`, `duration-seconds: 5`, рецепт 5 TNT + 4 `BLUE_ICE` |

**Риски.** Низкие. Ключ добавляется в record `Breaking` с дефолтом `true`
(поведение существующих конфигов не меняется), парсер — в
`DynamiteLoader`, санити-чек — в тесты.

### P2. Динамит Б2: куб вместо сферы

**Суть HW.** Б2 вырезает ровный куб 25×25×25 и **не работает на всех
стандартных заприваченных территориях** — только в дикой местности и на
нестандартных регионах.

**Что добавить.**

```yaml
breaking:
  # SPHERE — как vanilla (сфера по сопротивлению); CUBE — ровный куб.
  shape: SPHERE
  # Полусторона куба в блоках: 12 → куб 25×25×25, как Б2 на HolyWorld.
  half-extent: 12

regions:
  # true — на любом привате из QPS динамит не срабатывает вообще
  # (механика Б2: «не работает на стандартных территориях»).
  only-outside: false
```

**Реализация.** В `onExplode` при `shape == CUBE`: очистить
`event.blockList()` и собрать свой список обходом куба (с учётом
`isIndestructible`, `qps().canExplode` и бюджета `max-blocks`), после чего
прогнать его через тот же `processBlockList`. Куб 25³ = 15 625 позиций —
это много для одного тика, поэтому обязательно порционно, существующим
`schedulePending`.

`only-outside` — одна проверка: если `qps().regionAt(location) != null`
(нужного метода в QPS может не быть — проверить; есть
`QpsApi.flagAt`/`isTrusted`, при отсутствии — добавить в QPS или искать
регион по чанку), событие гасится с сообщением «здесь не сработает».

**Риски.** Средние: это самый тяжёлый по нагрузке динамит. Обязательные
меры — `max-blocks` в файле Б2 (например 15 625, но с порционной
обработкой), запрет `chain-radius` рядом с ним и предупреждение в лог при
power выше порога (такое уже есть).

### P3. Взрывчатое вещество — компонент крафта

> **Готово.** Пакет `component/`, файл `components.yml`, ингредиент вида
> `component:explosive` в рецептах динамитов, выдача через
> `/qtnt give component:explosive`.

**Суть HW.** Отдельный предмет-компонент: 9 пороха ↔ 1 веществу
(крафт обратимый — вещество можно разложить обратно в порох). Из него и
из динамитов A собирается Б2.

**Что добавить.** Небольшой пакет `component/` (или секция в
`config.yml`): описание предмета (`material`, `display-name`, `lore`,
`custom-model-data`), PDC-метка `qwetnts:component`, два рецепта
(9×`GUNPOWDER` → 1 компонент; 1 компонент → 9×`GUNPOWDER`) и возможность
использовать `component:explosive` в ингредиентах динамитов — по тому же
принципу, по которому сейчас работает `tnt:<id>` в
`CustomRecipeListener`.

**Риски.** Низкие. Механика PDC-рецептов уже есть и отлажена, нужно лишь
расширить множество допустимых «особых» ингредиентов с `tnt:` до
`component:`. Отдельно проверить, что обратимый крафт не создаёт
бесконечный цикл в верстаке (Bukkit такого не делает, но тест на
«результат не совпадает с ингредиентом» стоит добавить).

### P4. Бункер — стена замка и раздатчик

> **Готово.** Пакет `ru.qweyns.qwetnts.bunker`: `BunkerSettings`,
> `BunkerLoader`, `BunkerState`, `BunkerService`, `BunkerListener`.
> Файл `bunker.yml` в корне папки плагина, состояние — `bunker-state.yml`.

**Суть HW (lite/events/castle.md).** Замок стоит в 0;0. Внутри — бункер
за стеной из древних обломков. Пробить стену можно, выстрелив в неё из
раздатчика: у каждого типа динамита свой шанс пробития (ванильный TNT —
0,4 %, A — 0,8 %, B — 2 %, C4 — 5 %, Разрывная волна — 12,5 %, остальные —
0,4 %). Стена не исчезает сразу, а **деградирует**: древние обломки →
плачущий обсидиан → обсидиан → пробоина.

**Четыре решения, принятые администрацией** (набросок ниже был черновиком,
итог отличается в четырёх местах):

1. **Считаются только выстрелы из Тнт-пушки.** Снаряд помечается PDC
   `qwetnts:cannon-shot` в `CannonService.launch`. Подойти к стене с C4
   «в упор» нельзя: `BunkerListener` (приоритет `LOWEST`) вычищает блоки
   стены из `EntityExplodeEvent.blockList()`, а `DynamiteExplodeListener`
   пропускает их в `classifyBlock`, `scanHardBlocks` и при постановке льда.
2. **Стена деградирует целиком**, как на HW: один удачный ролл — минус одна
   стадия на всём прямоугольнике. За выстрел — **один** ролл (а не ролл на
   каждый задетый блок), иначе залп из десяти пушек крутил бы шанс десять
   раз подряд. Темп ограничивает `cooldown-millis` (по умолчанию 500 мс).
3. **Награду выдаёт не аддон.** При пробитии он выполняет список команд
   от имени консоли (`reward.commands`), а шалкер с добычей ставит тот
   плагин, который на сервере отвечает за ивенты. Подстановки в командах:
   `%player%` — кто пробил стену, `%world%`, `%x%`, `%y%`, `%z%` — центр
   стены. Так награда остаётся в ведении администратора и не тянет за
   собой зависимость от чужого формата лут-таблиц.
4. **Восстановление — и по таймеру, и вручную.** `respawn.interval-minutes`
   плюс команда `/qtnt bunker reset`; при `respawn.random-stage: true`
   стадия после восстановления случайна — слабая, средняя или прочная,
   как при появлении ивента на HW.

**Как это выглядит в конфиге** (итоговый `bunker.yml`):

```yaml
enabled: false
world: "world"
wall:
  from: [-8, 40, -8]
  to: [8, 55, 8]
  stages:
    - ANCIENT_DEBRIS      # первая ступень — самая прочная
    - CRYING_OBSIDIAN     # вторая
    - OBSIDIAN            # третья
    - AIR                 # четвёртая — всегда последняя
  hit-margin: 3        # на сколько блоков вокруг эпицентра считать попадание
  protect: true        # true — стену нельзя подорвать ничем, кроме шанса от пушки
chances:               # проценты за выстрел; дробные значения работают (0.4 — это 0,4 %)
  default: 0.4
  dynamite_a: 0.8
  dynamite_b: 2.0
  c4: 5.0
  shockwave: 12.5
  tnt: 0.4
cooldown-millis: 500   # пауза между засчитанными выстрелами
respawn:
  enabled: true
  interval-minutes: 60
  random-stage: true
announce: true
effects:
  on-degrade: { sound: block.ancient_debris.break, particle: EXPLOSION }
  on-breach:  { sound: entity.generic.explode, particle: EXPLOSION_EMITTER }
```

**Реализация.** `BunkerListener` ловит `EntityExplodeEvent`: сначала
снимает блоки стены со списка разрушения, затем передаёт выстрел в
`BunkerService.onShot`. Тот проверяет мир, зону (`wall.near` с запасом
`hit-margin`), метку пушки и кулдаун, после чего крутит шанс
`BlastMath.rollPercent` — дробный, чтобы 0,4 % не округлились в ноль. При
успехе `BunkerService` меняет стадию в `BunkerState`, рассылает сообщение
через `Schedulers.runGlobal` и планирует смену блоков **по чанкам** в их
«родных» регионах (`Schedulers.runAtLocation` — на Folia трогать блоки
чужого региона нельзя). Пробитие дополнительно даёт Discord-событие
`BUNKER_BREACHED` и запускает таймер респавна.

**Персист.** `BunkerState` пишет `bunker-state.yml` через `Io.writeAtomic`
(тот же паттерн, что у `RaidBlockManager`): стадия стены переживает
рестарт, иначе гриндивший её час игрок потерял бы всё.

**Деградация для обычных блоков (тот же механизм, что у стены).** Раз уж
цепочка ступеней написана, она пригодилась и вне бункера: секция
`transforms` любого динамита теперь поддерживает `chain` — список ступеней
сверху вниз, каждая снимается за один взрыв:

```yaml
transforms:
  chain:
    - ANCIENT_DEBRIS      # первая ступень — самая прочная
    - CRYING_OBSIDIAN     # вторая
    - OBSIDIAN            # третья
    - AIR                 # четвёртая — дыра
  chain-chance: 100
```

Включено у Разрывной волны, у C4 пример лежит в файле закомментированным.

Попутно вылез старый баг: у Разрывной волны древние обломки числились и в
`transforms`, и в `breaking.blocks`, а правило ломания проверялось раньше —
деградация не работала вовсе, хотя комментарий в файле обещал обратное.
Теперь цепочка проверяется до правил ломания (см. AUDIT, 10.3.15).

**Риски, которые оказались реальными.** Стена попадает и под собственные
правила динамитов (обсидиан ломает C4 по `breaking.blocks`), и под
`transforms` (древние обломки деградируют в обсидиан), и под временный лёд.
Поэтому стена вычеркнута из всех четырёх мест принятия решений о блоке, а
не только из `blockList`.

### P5. Рейд-блок по полному списку HW

По вики, райд-блок запрещает ставить: `OBSIDIAN`, `ENDER_CHEST`,
`CRYING_OBSIDIAN`, `ANCIENT_DEBRIS`, `ENCHANTING_TABLE`,
`RESPAWN_ANCHOR`. У нас в дефолтах — обсидиан, плачущий обсидиан, древние
обломки и (бесполезный, см. 10.3.10) укреплённый сланец.

Стоит: добавить три недостающих материала в `Materials.RAID_BLOCK_FAMILY`
и в дефолтные `raid-block.materials` у C4 и Разрывной волны. Одновременно
убрать оттуда `REINFORCED_DEEPSLATE`. Правка на 15 минут, закрывает
реальную дыру в анти-фениксе (эндер-сундук на месте пробоины — это
бесплатное хранилище, которое нельзя выбить).

### P6. Сервис и наблюдаемость

1. **Алерт владельцу привата** — 10.3.3: конфиг и класс уже существуют,
   не хватает отправки. Сообщение владельцу и участникам, что приват
   атакуют, чем и кем, сколько прочности осталось.
2. **`/qtnt info [id]`** — сводка по типу: мощность, радиус, урон осаде,
   правила ломания, рецепт. Сейчас это надо читать по четырём файлам.
3. **`/qtnt stats`** — счётчики сессии из `ExplosionStats`: взрывов по
   типам, выбито спавнеров, активных райд-блоков, уничтожено приватов.
4. **`/qtnt clear raid-blocks|temporary-blocks|placed`** — аварийная
   чистка, если что-то залипло. Сейчас помогает только удаление файла при
   остановленном сервере.
5. **События Discord** — сейчас только `REGION_DESTROYED`. Полезно
   добавить `REGION_UNDER_ATTACK` (первый удар по привату) и
   `BUNKER_BREACHED` (после P4): enum `DiscordEvent` уже готов к
   расширению.
6. **Публичное API** (`QweTntsApi` как статическая точка входа, по
   образцу `QpsApi`): `byId`, `byItem`, `ignite`, `launch`, `markRaid`,
   событие `QweTntsExplosionEvent`. Нужно, если аддон будут использовать
   другие плагины сервера; до первого такого запроса — не горит.

## 4. Что брать не стоит

* **Направленный (кумулятивный) заряд.** Интересная механика, но она не из
  HW Lite: там направленных подрывов нет, а баланс сервера она меняет
  сильнее всего. Оставить в «на подумать».
* **Апгрейд приватов, магазин эффектов региона, `/ps upgrade`,
  стоимость прочности.** Это ядро QPS. Дублировать их в аддоне —
  гарантированно разойтись с QPS при обновлении.
* **Свои регионы/приваты.** Аддон существует ровно для того, чтобы не
  изобретать защиту территорий.
* **Механику «заряда по клику» как единственный режим.** HW-механика
  (поджог отдельно) уже реализована и по умолчанию включена — откатывать
  не надо.

## 5. Порядок работ

```
P0 (дефекты) → P5 (список материалов) → P1 (неразрушающий режим + 3 динамита)
   → P3 (взрывчатое вещество) → P2 (куб Б2) → P6 (сервис) → P4 (бункер) ✅
```

P5 стоит делать попутно с P1 — это один проход по дефолтам конфигов.
P2 логически зависит от P3 (Б2 крафтится из вещества), поэтому вещество
раньше куба. Бункер — последний: он потребляет готовую пушку и
`transforms`, и его проще всего проверять на живом сервере.
